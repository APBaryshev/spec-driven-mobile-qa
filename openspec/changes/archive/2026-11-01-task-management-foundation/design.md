# Design

## Context

Мотивация и границы описаны в [proposal.md](proposal.md); поведение — в [спецификации](specs/task-management/spec.md). Репозиторий пока не содержит приложения, package manifest, конфигурации сборки или тестов. Значит, это создание основы с нуля, а не изменение существующей архитектуры. Design необходим из-за новой модели данных, зависимости хранения и асинхронного жизненного цикла.

## Goals / Non-Goals

**Goals:** простая структура с явным владельцем состояния, проверяемые правила названия, отсутствие потерь подтверждённых задач при последовательных операциях, безопасная загрузка, прозрачные ошибки, возможность расширять capability отдельными changes.

**Non-Goals:** универсальный repository framework, шина событий, глобальное состояние, произвольная замена всех зависимостей через контейнер, собственная база данных, журнал транзакций, резервное копирование, автоматическое исправление повреждённых данных, сохранение черновика после завершения процесса. Область продуктовых исключений — в proposal.

## Decisions

### 1. Expo и один функциональный модуль

Использовать минимальный Expo TypeScript-проект в корне текущего репозитория, без демонстрационных экранов и маршрутизации для одного экрана. Существующие README, OpenSpec и skills сохраняются при инициализации. Совместимые версии Expo, React Native, React и зависимостей фиксируются manifest и одним lockfile при реализации; номер SDK сейчас не выдумывается.

Предлагаемая структура будущей реализации:

```text
App.tsx
src/features/tasks/
  model.ts
  useTasks.ts
  taskStorage.ts
  TasksScreen.tsx
  components/
tests/
.maestro/
docs/
```

`App.tsx` связывает экран и конкретное хранилище. `model.ts` содержит типы и чистые правила. `useTasks.ts` владеет состоянием и операциями. `taskStorage.ts` содержит небольшой контракт и единственный AsyncStorage-адаптер. Компоненты выделяются по самостоятельной UI-ответственности, без обязательного отдельного файла для каждой обёртки. Дополнительная папка `domain`, слой use cases или универсальный `shared` пока не нужны.

Альтернативы: React Native без Expo даёт больше контроля над нативной инфраструктурой, но не решает дополнительной потребности MVP; Expo Router полезен при нескольких маршрутах, но сейчас создаёт лишнюю структуру. Архитектура использует кроссплатформенные API, проверенным выпуском считается только Android.

### 2. Модель данных и правила названия

Задача содержит только `id: string` и `title: string`. Генерируется UUID через совместимое с выбранным Expo SDK средство генерации; нельзя использовать индекс, название или только текущее время. При подготовке новой задачи ID проверяется на отсутствие в текущем списке. Сортировка по времени не нужна: порядок массива — порядок успешного создания, новый элемент добавляется в начало. ID сохраняется вместе с задачей, в том числе при перезапуске.

Название нормализуется удалением пробельных символов по краям по семантике ECMAScript `trim`. Затем проверяется отсутствие внутренних переводов строк: LF, CR (включая CRLF), VT (U+000B), FF (U+000C), NEL (U+0085), LS (U+2028), PS (U+2029). Внутренние пробелы сохраняются, регистр и Unicode-нормализация не меняются. Переводы строк не заменяются пробелами и не удаляются автоматически; при ошибке сохраняется весь исходный ввод. Однострочная настройка поля дополняет проверку в логике, включая вставленный текст. Визуальный перенос длинного названия в списке допустим и не означает наличие переводов строк в данных.

Согласованная длина в TM-01 — число кодовых точек Unicode, а не UTF-16 code units; составной emoji может занимать несколько символов. Внешняя библиотека сегментации графем не нужна. Ввод более 100 символов не обрезается молча: валидация объясняет ограничение. Проверяются длины 1/100/101, 99 букв + один emoji и комбинации с переводами строк.

Альтернативы: графемные кластеры ближе к визуальному восприятию, но требуют отдельного продуктового решения и проверки поддержки сегментации; обычная длина JS-строки неожиданно считает часть emoji за два символа. Даты, статусы и индексы сортировки добавляются только вместе с требованиями, которым они нужны.

### 3. Изолированное постоянное хранение

Минимальный контракт `TaskStorage`: `load()` возвращает проверенный список, `save(tasks)` сохраняет полный следующий снимок. Никаких деталей AsyncStorage в экране и правилах валидации. Конкретный объект передаётся в hook обычным аргументом; для тестов подставляется управляемое хранилище. DI-контейнер для этого не нужен.

В AsyncStorage один ключ `taskflow.tasks` содержит JSON-конверт с `schemaVersion: 1` и `tasks` в порядке отображения. Версия позволяет обнаружить несовместимый формат и позднее добавить миграцию. Отсутствующий ключ означает пустой список. Некорректный JSON, неподдерживаемая версия, неверные поля, невалидные названия и повторяющиеся ID означают ошибку восстановления всего снимка. Автоматический пропуск записей и сброс данных не выполняются. В MVP нет прежних форматов для миграции.

`save` разрешает promise после успешной записи адаптера. UI подтверждает создание после этого либо после контрольного `load`, подтвердившего весь отправленный снимок после ошибки записи. Rejection не означает доказанного отсутствия записи. Контракт `load`/`save` остаётся прежним: согласованием управляет существующий владелец состояния. Пустой массив при старте не записывается автоматически. Запись выполняется только явной операцией создания после безопасной загрузки и при отсутствии неопределённого исхода; effect, сохраняющий каждое изменение React state, не используется.

Альтернативы: SQLite обеспечивает более подходящие инструменты для сложных запросов и транзакционных изменений, но пока нет связей, фильтров и нескольких писателей. Полный JSON-снимок проще для небольшого списка, но каждая запись пропорциональна его размеру. Отдельные ключи задач требуют согласовывать индекс и записи. AsyncStorage не считается защищённым хранилищем секретов; названия не отправляются наружу и не попадают в логи.

### 4. Состояние и асинхронные операции

Один `useTasks` с React reducer хранит подтверждённый список и явные состояния загрузки/сохранения. Черновик принадлежит форме. Redux и Context не нужны: один экран не имеет удалённых потребителей общего состояния.

```text
loading --> ready
   |
   v
loadError --> loading

ready --> saving --> ready
             |
             v
         reconciling --> ready       (sent snapshot found)
             |
             +--> saveError          (base snapshot found)
             |
             +--> outcomeUnknown --> reconciling

saveError --> saving                 (explicit retry)
```

`loadError` не содержит выдуманного пустого результата. `saveError` означает проверенное отсутствие результата записи и сохраняет список/ввод; `outcomeUnknown` означает, что новые записи небезопасны. Эти состояния не подменяются обычной ошибкой первоначального чтения. Один `useTasks` владеет записями на протяжении экранной сессии; дополнительные писатели и параллельные экземпляры для одного ключа не допускаются.

Создание: проверить readiness и синхронный in-flight guard; нормализовать и проверить название; подготовить ID и снимок из актуального подтверждённого списка; занять guard до первого `await`; заморозить поле и отправку. В памяти сохранить неизменяемую попытку: исходный снимок, отправляемый снимок, ID и исходный текст. При успешном `save` опубликовать снимок, очистить ввод и завершить попытку. При rejection не снимать запрет новых записей, перейти к контрольному чтению. Отключение кнопки дополняет guard, а не заменяет его: React render может отстать от нескольких быстрых событий. Валидация и guard применяются ко всем способам отправки формы.

Контрольное чтение выполняется после завершения ошибочной операции записи и при отсутствии внешних писателей. Операции не перекрываются. Таймаут не считается отменой записи и не разрешает начинать согласование параллельно ещё выполняемой записи. Пока promise не завершился, сохраняется блокировка. Контракт выбранной версии адаптера должен обеспечивать, что завершившаяся операция больше не выполняет отложенных записей; эти предпосылки проверяются при интеграции. Механизм не является транзакцией, CAS или защитой от произвольного аппаратного сбоя.

Результат `load` валидируется и семантически сравнивается с обоими снимками: версия формата, полный набор задач, точные ID/названия и порядок. Проверки только по наличию ID попытки недостаточно. Отсутствующий ключ сопоставим с исходным пустым состоянием первого запуска; исчезновение ключа при непустом исходном списке — неожиданный результат.

| Контрольное чтение | Переход и действие |
| --- | --- |
| Полностью совпадает с отправленным снимком | Принять его как подтверждённый список, очистить поле, сообщить об успехе; повторный `save` не выполнять |
| Полностью совпадает с исходным снимком | Перейти в `saveError`, показать ошибку записи, оставить исходный ввод и список; разрешить исправление или явный повтор создания |
| Чтение не удалось, формат повреждён или снимок отличается от обоих | Перейти в `outcomeUnknown`, оставить ввод и подтверждённый список; запретить изменения поля и новые записи, разрешить только повтор проверки чтением |

Повтор из `outcomeUnknown` использует те же исходный/отправленный снимки и не вызывает `save`. Одновременно допускается только одно контрольное чтение; action guard не позволяет повторным нажатиям запустить второе. Запрет новых записей действует также между проверками. Автоматический merge, подмена исходного списка неожиданным снимком и перезапись «для исправления» не выполняются. Исходные данные остаются нетронутыми; при неожиданном снимке безопасная блокировка может быть длительной.

После подтверждения исходного снимка повтор неизменённого ввода использует прежний ID и снимок. Исправление ввода разрешено только после определения исхода; изменённый ввод начинает новую попытку из актуального подтверждённого списка. Если контрольное чтение подтвердило задачу A, последующее создание B строит снимок `[B, A, ...]`, поэтому A не теряется. Если подтверждено отсутствие A, создаётся только B. При новой ошибке записи снова выполняется тот же протокол. Неограниченные автоматические повторы не вводятся.

Повтор первоначальной загрузки доступен из `loadError`; повтор проверки исхода — из `outcomeUnknown`. Эффект начальной загрузки не пишет данные. Результаты отменённого lifecycle-поколения игнорируются (cleanup/token), ошибки promises обрабатываются. Размонтирование не считается отменой выполняемой нативной записи: нельзя создавать нового писателя или начинать загрузку поверх неё в том же процессе; перед повторной инициализацией нужно дождаться её завершения. Обычные Strict Mode-повторы начальной загрузки остаются только чтением. Для одного экрана достаточно одного владельца записи и guard, универсальная очередь CRUD не нужна.

Альтернатива слепого повтора с прежним ID недостаточна: изменение ввода после фактической записи могло бы затереть её устаревшим снимком. Контрольное чтение обнаруживает исход до разрешения следующего изменения. Журнал или отдельные ключи попыток добавили бы согласование нескольких записей без транзакций; для текущего одного писателя это неоправданно.

### 5. Жизненный цикл и восстановление

Запись начинается при создании, не при уходе в фон и не в cleanup. Возврат из фона не повторяет создание и не запускает загрузку поверх текущего состояния: внешних писателей нет. Новый процесс всегда читает постоянный снимок. Не делаем зависимую от платформы обязательную фоновую работу для сохранения данных.

Успешно завершённая запись либо контрольное чтение, подтвердившее отправленный снимок, — доступная приложению граница подтверждения. Это не обещание устойчивости к физическому отказу накопителя или произвольному сбою ОС. Остановка до подтверждения может оставить задачу сохранённой или несохранённой; после нового запуска отображается фактический валидный снимок. Данные после очистки приложения и переустановки вне контракта.

При остановке процесса во время `saving`, `reconciling` или `outcomeUnknown` попытка, снимки в памяти и черновик не восстанавливаются как команда. Следующий запуск выполняет только обычный `load` с блокировкой создания до успешного чтения. Если задача записалась, она восстанавливается один раз с прежним ID; если нет — автоматически не создаётся. При ошибке чтения действуют TM-07/TM-08; автоматического `save`, восстановления старого снимка или повторного создания нет. В integration это проверяется новой сессией с тем же хранилищем для обоих возможных постоянных результатов, включая ошибку чтения на старте. Возврат из фона в том же процессе сохраняет текущую попытку/блокировку и не запускает параллельный протокол.

Повреждённый снимок остаётся нетронутым; повтор помогает при временном сбое, но не исправляет постоянно повреждённый формат. Экран сообщает, что загрузка не удалась, а не что задач нет. Сброс, экспорт или восстановление из резервной копии требуют отдельного change, поскольку вводят новые действия и риски потери данных.

### 6. UX, доступность и ошибки

Один экран: заголовок TaskFlow, поле названия, действие создания, список либо пустое состояние. Во время начального чтения — явная загрузка; при ошибке чтения — отдельная панель с повтором. При сохранении и контрольном чтении список остаётся доступен для просмотра, поле и отправка недоступны; подпись различает «Сохранение» и «Проверка результата сохранения». После подтверждённого успеха ввод очищается. Если контрольное чтение подтвердило исходный снимок, ошибка записи у формы сохраняет черновик и позволяет исправление/повтор отправки. Если исход неизвестен, сообщение объясняет неопределённость и действие «Повторить проверку» выполняет только чтение; поле и создание остаются недоступны. Успех или отсутствие задачи не объявляются по одной ошибке ответа. Валидационная ошибка исчезает после исправления/повторной проверки, предыдущая ошибка записи — при следующей попытке.

Использовать нативные доступные элементы, роли, labels, disabled/busy state, текстовые ошибки и Android announcement/live region по необходимости. Читаемые названия строк с переносом, виртуализированный список, safe area и компоновка с учётом клавиатуры. Поля и действия доступны при стандартном и увеличенном системном шрифте; точный визуальный стиль не является отдельной дизайн-системой MVP.

Предлагаемые значения по умолчанию: интерфейс на русском, нейтральная системная тема, без анимаций переходов и отдельного экрана создания. Точный текст ошибок можно уточнить без изменения поведения. Технические stack traces, сырые исключения и названия storage keys не выводятся пользователю. Диагностика содержит категорию операции/ошибки без названий задач, сырых снимков и небезопасного текста исключений.

### 7. Проверки и прослеживаемость

Unit: нормализация, запрет внутренних переводов строк, Unicode-границы названия, переходы reducer и порядок. Уникальность ID проверяется для одинаковых названий и при искусственной коллизии генератора с ID существующей задачи: совпавший ID не принимается, существующие ID неизменны. Эти тесты доказывают инварианты логики, а не математическую невозможность коллизии UUID. Внешняя библиотека графем не используется.

Integration: настоящий модуль задач и адаптер сериализации с управляемой границей key-value I/O. Проверять точное равенство ID до/после round trip и новой сессии с тем же хранилищем, включая одинаковые названия. Контролируемые promises проверяют медленную запись, быстрые повторы, отказы I/O, устаревшие результаты и отсутствие преждевременного успеха. Обязательные ветки согласования: сохранить значение и вернуть ошибку; вернуть ошибку без изменения значения; ошибка контрольного чтения; повреждённый/неожиданный снимок; успешный повтор только чтения; новая задача с изменённым названием после каждого определённого исхода; остановка сессии во время проверки и новая безопасная загрузка без повторной записи. Сверять все ID, названия и порядок, число `save` и последовательность завершения записи перед контрольным `load`. Использовать Jest с `jest-expo` и React Native Testing Library; не подменять саму проверяемую логику mock-результатами.

Maestro E2E на Android: чистый старт, создание, ошибки ввода, повторяющиеся названия, порядок, остановка и новый запуск без очистки данных между созданием и проверкой. Отдельно проверить автономность на устройстве/эмуляторе без сети. Нативный адаптер подтверждается сохранностью после остановки процесса в устанавливаемой сборке со встроенным JS bundle и собственным application ID; Expo Go не является единственным доказательством. Ошибки I/O воспроизводятся в integration, без production-переключателей отказа или тестовых экранов. TalkBack, клавиатура и увеличение шрифта проверяются отдельно вручную с записанным результатом.

Стабильные `testID` поддерживают автоматизацию; доступные labels нужны пользователям. Вложенность не должна скрывать элементы из accessibility tree. Селекторы не зависят от координат и порядка строк; пользовательский результат проверяется по видимому тексту, числу задач и их порядку. Maestro не считается доказательством сохранности внутренних ID: это ответственность unit/integration. Не добавлять технические подписи, скрытые экраны или специальные accessibility labels для вывода ID ради E2E. Фиксированные sleeps не заменяют ожидание результата.

Будущая `docs/traceability.md` связывает TM-ID, имена сценариев спецификации, пути и названия тестов, результаты. Связи до отдельных сценариев важнее формального процента покрытия. Один сценарий может подтверждаться несколькими уровнями, каждая связь имеет обоснование. До фактического прогона статус — «не проверено». README описывает воспроизводимый запуск с чистого checkout; отчёт — commit, build identifier, версии инструментов, устройство/API, команды, результат и ссылки на логи. В публичные доказательства входят только синтетические данные. Документы, исходники и конфигурации создаются независимо в этом репозитории.

Сопровождаемость проверяется strict TypeScript, линтером, тестами инвариантов и review направления зависимостей: UI не обращается к AsyncStorage напрямую, чистые правила не импортируют UI или нативные API. Произвольные пороги покрытия и времени отклика не вводятся без базы измерений. Проверки с задержанным I/O дают наблюдаемый критерий отзывчивости; размеры списка и latency можно измерить и уточнить отдельным change.

Технические источники: [Expo: хранение](https://docs.expo.dev/develop/user-interface/store-data/), [Expo: Jest и React Native Testing Library](https://docs.expo.dev/develop/unit-testing/), [Maestro: React Native](https://docs.maestro.dev/get-started/supported-platform/react-native), [Maestro: запуск и очистка](https://docs.maestro.dev/reference/commands-available/launchapp). Совместимость конкретных версий проверяется при инициализации, а не предполагается по документации latest.

## Risks / Trade-offs

- Полный JSON-снимок растёт вместе со списком → виртуализация UI и последовательные записи для MVP; при реальном росте измерить и обосновать SQLite отдельным change. Лимит числа задач не вводится скрыто.
- Контрольное чтение не является транзакционной защитой → выполнять его после завершения ошибочной записи, при одном владельце и отсутствии внешних писателей; не считать timeout отменой, проверить последовательность I/O и контракт завершения выбранного адаптера. Произвольные поздние записи/аппаратные сбои вне гарантий.
- Невозможность установить исход оставляет создание заблокированным → сохранять ввод/снимки и разрешать повтор чтения, не пытаться исправлять состояние слепой перезаписью. Это осознанный компромисс сохранности против доступности записи.
- Постоянно повреждённые данные не исправляются повторным чтением → сохранить оригинал и показать ошибку; согласовать отдельно, нужен ли пользовательский сброс/экспорт в будущем.
- Длина в кодовых точках отличается от визуальных графем → согласованное правило TM-01 и граничные проверки emoji без внешней библиотеки графем.
- Нет сохранения черновика при завершении процесса → явно ограничить обещание сохранности подтверждёнными задачами.
- Изменения формата будущими changes могут затронуть старые установки → версия снимка, отказ от молчаливого сброса, отдельная миграция до изменения формата.
- Сборки Android и тестовый runtime зависят от совместимых версий → зафиксировать SDK, зависимости, lockfile и воспроизводимые команды; не считать iOS проверенным по факту использования React Native.

## Migration Plan

Существующих пользовательских данных и релизов нет. В реализации: безопасно добавить Expo-проект, зафиксировать совместимые зависимости и application ID, реализовать формат v1, выполнить проверки, собрать устанавливаемый Android-артефакт и записать результаты. На этом этапе ни один пункт не выполнен.

Откат до первого выпуска — откат кода/сборки без удаления пользовательских данных. Последующие версии обязаны учитывать формат v1; несовместимый downgrade не должен молча очищать хранилище. Синхронизация delta spec с main specs и архивирование выполняются позднее отдельно от реализации.

## Open Questions
